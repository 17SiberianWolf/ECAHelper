## 2. 分期计划

### 批次 1 —— "修复与交互"（对应 P0 + 体验类 P1）

| ⑥ **全站同类缺陷排查**（见 §3.1 排查清单） | 问题 1 延伸 | P0 |

### 批次 2 —— "口径与观测"（对应口径 P1 + 增强类 P2）

| 条目 | 对应问题 | 优先级 |
|---|---|---|
| ⑦ 项目号父/子归并（全面生效 + 子项目下钻 + 导出父号主列/原始号列） | 问题 2 | P1 |
| ⑧ 日志系统：文件日志 + SQLite 审计表 + 「系统日志」新页面 | 问题 7 | P2 |

### 为什么这样切分

1. **风险隔离**：批次 1 全是**前端与直接可见的修复/交互**，改动面集中在 `web/static/js/app.js`、`web/static/css/style.css`、`web/templates/*`，**不触碰统计口径与数据库**，可快速交付并拿到用户反馈。
2. **依赖顺位**：批次 2 的「项目号归并」会改变下拉、统计、Top N、导出四处的**取数口径**，需要独立的红线条线验收（§附录 B 硬指标 ①②），放在缺陷修复之后，避免把"口径变化"与"缺陷修复"混在同一次提交里，难以定位问题。
3. **前端基础设施先行**：「可搜索下拉」（批次 1）是「系统日志筛选」「任务说明」等后续交互的公共组件，先落地可复用。
4. **日志与归并相互独立**：二者都不依赖批次 1，但都涉及"取数/落库"层面，合并在批次 2 便于集中做数据一致性验收。

## 3. 需求详述（用户故事 + 可验证验收条件）

> 约定：`→` 表示因果；验收条件优先给**可执行的数值断言**或 **Given/When/Then**。

### 3.1 问题 1 ｜缺陷：员工工时查询"查不出结果"（P0．批次 1）

**已确诊现状（直接采信，不重复调研）**：
- `web/static/css/style.css` 定义 `.hidden{display:none}`；`web/static/js/app.js` 的 `bindTabs()` 切换标签时写 `el("chartArea").style.display = ""` —— **内联清空无法覆盖 CSS 类规则**。用户点过「图表」标签后，`#result` 被置 `display:none`，而 `#chartArea` 因 `.hidden` 类永远显示不出来 → **整页空白**。
- `renderThreeLayer()` 第 3 张表固定读 `result.by_person`，但员工查询接口返回的是 `by_project`（且传了 `personLabel:"项目"`），导致员工页多渲染出一张**空的「按项目」表**。
- 顶部卡片「项目数」用的是 `total.persons`（distinct `resource_id_norm`），单查一人时**恒为 1**，是错的。
- 后端无问题：实测 `ZHXU01` 查 `2026-01..2026-09` 返回 **25 行 / 1467 h**。

**用户故事**

> **US-R2-01**：作为项目经理，我希望点击「图表 / 三层结果」标签来回切换后，无论当前在哪个标签，都能正常看到对应的结果区或图表区，以便我不会误以为"这个人查不出工时"。

> **US-R2-02**：作为项目经理，我查询单个员工时，希望结果区展示的是**这个人的项目分布 + 非项目工时**（而不是一张空的"按项目"表），并希望顶部卡片显示真实口径的数字，以便我能正确读懂结果。

**验收条件（可验证）**

- **AC-01-1（标签回归）**：Given 已有一次查询结果；When 依次点击「图表」→「三层结果」；Then 两个标签的内容都能正确显示（不再出现空白），且 `#chartArea` 的可见性由 JS 显式控制（不再依赖"清空内联样式"）。
- **AC-01-2（控制台）**：上述切换过程中，浏览器控制台 **0 报错**。
- **AC-01-3（员工页三层）**：Given 查询 `ZHXU01` / `2026-01..2026-09`；Then 返回 **25 行 / 1467 h**，结果区**不再出现空的「按项目」表**，改由接口实际返回的 `by_project` 正确渲染为「按项目明细」。
- **AC-01-4（计数修正）**：Given 单查 1 人；Then 顶部卡片不再显示被误用的「项目数 = persons（恒为 1）」，改为按接口真实维度展示（单查一人时"人员数"应为 1，且项目维度以 `by_project` 长度为据）。
- **AC-01-5（口径自洽）**：三层合计等于 `total.total_h`（顶部总计 = 各月之和 = 各明细之和）。

**⑥ 全站同类缺陷排查清单（批次 1 一并交付）**
- 全站所有使用 `.hidden` 类 / `style.display` 组合切换可见性的代码点（含 `three_layer` 折叠区、图表面板、导入结果区、加载中 spinner）；
- 所有 `renderThreeLayer` 调用点的 `personLabel` / `projectRows` 参数与实际接口返回结构是否匹配（项目页 / 员工页 / 综合检索页三处）；
- 所有顶部卡片的 `total.*` 字段是否与该页真实维度一致；
- 折叠交互（`.collapse-head` 事件委托）在切标签后是否仍有效。

> **实现提示（非需求）**：建议统一改为**切换 CSS 类**（增删 `hidden`）而非写内联 `display`，从根上避免"内联 vs 类规则"冲突；`renderThreeLayer` 改为按接口返回的键（`by_person` / `by_project`）动态渲染，避免写死。

### 3.2 问题 4 ｜「任务」字段不可用（P0．批次 1）

**现状**：`task` 字段有 **1,175 个不同取值**，大量是自由文本长句（如 `Test the Habas RCL L2&L3 interface and waiting for the site.`）；检索接口用 `r.task = :task` **精确相等**匹配；现 UI 只是一个自由文本输入框（`web/templates/search.html` 中 id=`taskSel`，placeholder「可选」）。

**用户故事**

> **US-R2-03**：作为项目经理，我希望「任务」是一个**可搜索的下拉**，列出数据中实际存在的任务值（按累计工时降序），并配上中文说明让我一眼看懂每个值代表什么；同时我仍能手动输入列表外的值；筛选时按**包含匹配**而非精确相等，以便我能方便地按"工作类别"（如休假、采购服务、项目管理）过滤工时。

**验收条件（可验证）**

- **AC-04-1（可发现）**：任务下拉选项**来自实际数据**，按累计工时**从高到低**排列；出现常见值：`Leave` / `Procurement services` / `Application Software` / `Aquisition (project in a offer phase)` / `Sales projects` / `Automation Hardware` / `General activities` / `Project management` / `Office Work` / `Site activities`。
- **AC-04-2（可理解）**：每个任务选项旁展示**中文说明**（如 `Leave = 休假`、`Procurement services = 采购服务`、`Project management = 项目管理`；对照表见 §4.3，需用户确认）。
- **AC-04-3（可输入）**：输入关键字可实时过滤选项并高亮命中片段；**允许提交列表外的值**（自由文本仍生效）。
- **AC-04-4（匹配语义）**：Given 任务输入 `Procure`；When 查询；Then 命中所有 `task` 包含 `Procure` 的行（**包含匹配**，不再是 `=` 精确匹配）。
- **AC-04-5（说明文案）**：字段下方有一行辅助说明，明确"任务 = 该行工时归属的工作类别"。
- **AC-04-6（全量可选、无静态截断）**：前端**一次性载入全部候选值**（任务 1,175 / 项目 1,262 / 组织 78 / 成本中心 48 / 人员 260，量级很小，纯内存数组即可），输入时在**内存中做包含匹配**、**只渲染前 50 条**匹配项（避免一次渲染上千条）。**不设静态 Top N 截断**——因此**任何取值（含排在第 500 名的任务值）都能被关键字命中**，不会重演正在修复的"查不到"问题；仍允许输入列表外的任意值。

> **实现提示（非需求）**：后端检索 `task` 由 `=` 改为 `LIKE '%kw%'`；需新增"任务选项"读取接口（返回**全部** `task + 累计工时`，降序）。前端**全量载入 + 内存包含匹配 + 只渲染前 50 条**（见 AC-04-6），杜绝"选不到的取值"这一功能漏洞。

### 3.3 问题 2 ｜项目号父/子被拆开统计（P1．批次 2）

**规则（用户确认，不可改动）**：**取第 2 个 `.` 之前的字符；不足 2 个点则原样保留。**
- `O 1100.036.01.01.0028` → `O 1100.036`
- `O 1100.033.01` → `O 1100.033`
- `0.0001` / `OE1323.172` / `70463` → 保持原样

**实测影响面（直接引用）**：项目号 **1,552 → 1,262** 个；仅 **422 个 / 4,449 行 / 184,694.0 h** 被归并；**无点号 308 个 + 仅 1 个点 822 个**（约 **129 万工时，占 82%**）不受影响；归并后**总工时守恒 1,474,383.8 h**；归并规则已用纯 SQL 表达式对全部 **1,552 个项目号逐条比对，0 处偏差**。

**用户故事**

> **US-R2-04**：作为项目经理，我希望统计、排行与导出都按**父项目号**汇总，这样同一个项目下不同子号（WBS 级）的工时会合并成一行；同时我希望**仍能下钻看到子项目号明细**。

> **US-R2-05**：作为项目经理，我希望导出的文件以**父项目号为主列**，并**额外保留一列"原始项目号"**，这样德国老板能看到汇总口径，我也能追溯到原始写法。

> **US-R2-06**：作为项目经理，我希望「按项目」表里的父项目号**可展开**查看其名下各子项目号的明细；而原有的 **WBS 下钻**能力收进一个**可折叠区块**而不是被删掉。

**验收条件（可验证）**

- **AC-02-1（归并生效面）**：Given 一次全量统计；Then 项目下拉、统计聚合、Top N 排行、导出**四处**全部使用父项目号口径；下拉项数由 1,552 变为 **1,262**。
- **AC-02-2（红线守恒）**：Given 全量数据；Then 行数仍为 **33,015 行**、全量工时仍为 **1,572,771.8 h**、归并口径工时仍为 **1,474,383.8 h**（**不因归并丢失或增加任何工时**）。
- **AC-02-3（交叉核对）**：Given 父项目 `O 1100.036`；Then 其工时 = 该项目名下**各子项目号**的工时之和（父 = 各子之和，可逐项核对）。
- **AC-02-4（下钻能力保留）**：Given 在「按项目」表中点击父项目号；Then 可展开看到其名下的子项目号明细；WBS 下钻以**可折叠区块**形式仍可访问，功能未删除。
- **AC-02-5（导出列）**：导出的 Excel / CSV 表头包含双语列 `Project ID / 项目号`（父号主列）与 `Project ID (raw) / 原始项目号`（原始写法列）。
- **AC-02-6（不变式）**：归并规则对 `0.0001` / `OE1323.172` / `70463` / 单点号值不产生任何改写。

> **实现提示（非需求）**：归并用 SQL 表达式实现（不改表结构、不重导）；原始项目号来源为既有的 `timesheet_record.project_id_raw`，**无需新增列**。

### 3.4 问题 3 ｜日期控件难用（P1．批次 1）

**现状**：项目工时 / 员工工时 / 综合检索 **3 个页面**均使用原生 `<input type="month">`，Chrome 下切换年份非常费劲。

**用户故事**

> **US-R2-07**：作为项目经理，我希望用**两个下拉（年 + 月）**来选日期区间，以便我能快速跳到任意年份，而不用忍受原生月份控件的别扭操作。

**验收条件（可验证）**

- **AC-03-1（控件形态）**：3 个页面的「起 / 止」日期均改为**「年下拉 + 月下拉」两个原生 `<select>`** 组合（零依赖、离线、约 40 行原生 JS）。
- **AC-03-2（年份覆盖）**：年份下拉覆盖数据实际范围（`2023-02 ~ 2026-09`），可直接选中任意年份（含 2023）。
- **AC-03-3（快捷按钮兼容）**：「今年 / 去年 / 全部 / 当前季」快捷按钮仍能正确**回填**年、月两个下拉。
- **AC-03-4（提交一致）**：查询提交的区间字符串仍为 `YYYY-MM`（与后端契约不变），与改造前结果**完全一致**。

### 3.5 问题 6 ｜下拉框不可搜索/不可手输（P1．批次 1）

**现状**：项目号(**1,262) / 组织(78) / 成本中心(48) / 人员(260) / 任务(1,175)** 全是原生 `<select>`，选项多时只能滚动查找。
